# Ballance Mod Loader Runtime Context

This context names the loader-owned runtime features that ship with BML itself. It distinguishes the built-in Mod's lifecycle role from the player-facing features it owns.

## Language

**Built-in Loader Mod**:
The loader-owned Mod registered with the id `BML`. It receives Mod lifecycle callbacks and owns the built-in runtime features without absorbing their state and behavior.
_Avoid_: BML service, built-in feature

**Built-in Console**:
The loader's in-game command surface, comprising the command bar, message board, command history, built-in command registration, and their configuration. One Built-in Loader Mod owns one Built-in Console.
_Avoid_: CommandBar, MessageBoard, console UI

**Built-in HUD**:
The loader's in-game status and custom overlay surface, comprising the HUD tree, title, FPS display, speedrun timer, cheat indicator, HUD command, and their configuration. One Built-in Loader Mod owns one Built-in HUD.
_Avoid_: HUD window, HUD host, HUD service

**Built-in Custom Maps**:
The loader's custom-map feature, comprising map discovery, map selection, temporary map preparation, game-script bindings, level selection, and its configuration. One Built-in Loader Mod owns one Built-in Custom Maps Module.
_Avoid_: map menu, map loader, custom map service

**Built-in Gameplay Tweaks**:
The loader's configurable game corrections, comprising the lantern alpha-test option, life-ball freeze fix, overclock patch, and their Virtools script bindings. One Built-in Loader Mod owns one Built-in Gameplay Tweaks Module.
_Avoid_: script patches, tweak settings, gameplay fixes

**Built-in Game Event Hooks**:
The loader-owned Virtools script adapters that translate game and menu transitions into Mod lifecycle and gameplay callbacks. One Built-in Loader Mod owns one Built-in Game Event Hooks Module.
_Avoid_: EventHookRegistrar, callback patches, event bridge

**Behavior Authoring**:
The public `bml.behavior` interface through which a Native Mod opens a Session, selects a registered Prototype, configures a copyable Block, and creates a Call, Task, or Instance that owns one real `CKBehavior`. Call executes once and requires explicit Continue, Task delegates later continuation to the Loader, and Instance is driven by Pulse; these are execution permissions over the same native lifetime, not separate Behavior kinds. A Block names its Target, Setting stages, Pins, Locals, and default Frame retention. Each Settings call is one native stage because `SETTINGSEDITED` may rebuild the Layout before the next stage is resolved. A run owns copied Frames containing the active Outs and Pout parameter values observed for each native Execute. Object-valued Pouts hold a `BML_ObjectRef` issued while the value still names a live CK object; taking a Frame never reads the original CK parameter or object again. The same interface inspects live graphs, observes graph/value changes, and accepts one symbolic Edit either as a Patch on an exact graph snapshot or as a Plan reconciled against exact-name scripts in later worlds. Every facade value created from a Session shares ownership of that native Session; releasing the original Session value does not invalidate a Block, run, Watch, Plan, or Patch that still needs it, and the last such value closes the native Session. A Plan or Patch remains readable while its inverse is Closing or Conflicted; once Close has requested retirement, the Loader retries unfinished inverses at later Behavior safe points even when the facade value has been destroyed. Sessions belong to one Native Mod generation, survive a world reset, and stop admitting work when that owner retires.
`BML::Behavior::Sessions` owns the owner-scoped Session and Run records behind this interface. It is not a second Behavior model: it delegates each native Instance to Behavior Runtime, and every Run retains both that Instance and its copied Frames until explicit Run/session/owner/world teardown. A `Ready` Run has no pending native or queued continuation; it does not assert that manager registrations, callback work, Locals, or other state established by the BB have ended. Call, Task, and Instance describe execution admission and continuation, not three different native lifetime policies.
`BML/Behavior.hpp` is the thin umbrella for the typed Native C++ facade over that same C seam; the public domain headers are split into Value, Prototype, Frames, Graph, Run, Block, Edit, and Session, while caller-buffer lowering and callback thunks remain in `Behavior/Detail`. `Session::Use` returns a Block directly. A Block is a copy-on-write configuration value: unchanged copies share owned author data and the validated C descriptor, while changing Target, Settings, Pins, Locals, or Frames invalidates only that copy. Validation is optional because the first execution performs the same work; its first success pins the provider generation so a replacement provider makes the Block stale instead of changing implementations. The facade exposes Prototype discovery and declared Layout directly, returns distinct move-only Call, Task, and Instance handles, uses `PulseResult` for immediate versus queued input, and stores wire results in reusable `Frames` buffers. Frame, Out, and Pout are read-only views invalidated by the next modification of their owning Frames; typed Pout access validates the complete wire batch before exposing any view. Each run can read its live Layout or inspect the graph of the native Behavior it already owns without a Scene name lookup. A live Layout Slot carries its layout generation: `Set` writes a Pin or Local, `Bind` connects a Pin to another live parameter with Virtools direct/shared source semantics, and `Settings` applies another Setting stage before restoring the run's current Target, Pin, and Local bindings against the resulting Layout. The facade does not implement a second scheduler, parameter model, graph model, result store, or public construction process.
`BML::Behavior::PrototypeCatalog` is the private catalog behind Prototype discovery. It owns copied declaration and provider metadata, assigns a process-monotonic generation to each provider registration, and invalidates cached declared layouts when Virtools retires a declaration. A `PrototypeRef` is the Prototype GUID plus that provider generation; it prevents a previously discovered Block from silently binding to a replacement DLL. Discovery is exposed only when declaration retirement can be observed reliably, and provider reload requires all live Runs from that provider to be closed first. Ballanced exposes no Prototype metadata that proves a BB can run without a parent graph, so production discovery does not infer or learn detached compatibility from GUIDs or successful calls. An unclassified Prototype remains usable and reports `DetachedSupport::Unverified`; any future authoritative classification is scoped to the provider generation.
A declared Layout describes the Prototype contract without creating a `CKBehavior`; a live Layout describes one configured Run after Setting callbacks and dynamic layout changes. Both use the same Slot vocabulary and parameter descriptions. `BML::Behavior::Value` owns copied Raw, Text, and typed-Null literals without consulting a CK world. `BML::Behavior::Parameter::Binding` represents a live object, a copied parameter, or a Direct/Shared source; the Parameter module also owns `CKParameterManager` descriptions, Virtools type compatibility, native writes, and the managed input/source relations that retain Runtime-created parameters. Neither is a second codec or type registry.
`Inspect` returns an owned Logical or Live view of a native Behavior graph: Nodes, Ports, Links, delay state, Prototype identity, and stable per-view fingerprints contain no borrowed CK pointer. Live is the physical CK graph. Logical is the author-visible graph: explicit Add and Flow edits remain visible, while CKEdit restores each claimed anchor's base endpoints and delay and hides only the exact Splice continuation, Tap/After HookBlock, and observer Link identities recorded in its journal. CKGraph never guesses infrastructure from a name or shape; if a claimed physical after-image no longer matches, Logical inspection reports `GraphChanged`. `Read` observes stored or direct/shared parameter values without evaluating a Parameter Operation; an operation is reported as indeterminate. Node names are not identities: `FindAll` returns every owned match, while `Find` fails on missing or ambiguous names. A Watch compares graph, layout, or sampled values once per game frame and uses the shared callback lease protocol. Observation or author-callback failure leaves the Watch readable in its Failed state with the first diagnostic and stops later polling. Portable CK2.1 does not publish exact data-change observation; delayed-list membership remains unknown instead of being inferred from residual values.
`BML::Behavior::Topology` is the private logical control-flow model behind graph editing. A native anchor identifies one logical Link independently of its source/sink shape; each Link retains its base endpoints and delay. Patch overlays are ordered as whole `(owner, patch)` groups by explicit Before/After relations and the stable `(priority, owner, patch)` key, while Out taps remain a separate family. Candidate replacement is atomic, cycles and cross-Link ordering targets leave the current topology unchanged, and fingerprints do not depend on Patch installation order. Topology validates intent only; it does not mutate a CK graph.
The public `BML::Behavior::Edit` is one symbolic graph transformation. Its nested Node, Port, Link, and Path values are authoring symbols rather than graph-snapshot objects. It names nodes and exact links, snapshots configured Blocks at Add, and combines Flow, Bind, Share, Push, Tap, Splice, and per-kind dynamic interface changes in one declaration order. The same Edit can be applied to one exact Logical Graph snapshot or retained by a Plan. Patch application admits `Use(Node)` and `Use(Link)` identities from that snapshot; Plan validation rejects those world-bound values and retains only semantic queries, Prototype GUIDs, copied literals, and symbolic actions for later worlds. A dynamic Port has only an Edit-local identity until each current Layout supplies its live index. The public Edit lowers to the private durable `GraphEdit`, which compiles a resolved private `Edit` against the current Logical Graph for each installation. Validation keeps graph locality, Virtools parameter compatibility, existing and proposed data relations, overlay order, and newly formed same-frame cycles ahead of native mutation. `BML::Behavior::CKEdit` applies the resolved candidate and owns its Patch journal. Exact Splice preserves the native anchor Link, its pending membership, and its remaining delay while `Topology` materializes the ordered overlay chain; world-scoped topology is discarded when the graph has no active Patch so CK object-id reuse cannot inherit an old graph.
`BML::Behavior::Patches` is the Loader-owned collection of live Patch installations and the production compiler for `GraphEdit`. It binds each Patch to a Session owner generation, retains the `CKEdit` journal, advances queued Apply and Close at the Behavior safe point, and closes installations during owner retirement, graph deletion, or world reset. `BML::Behavior::Plan` owns a durable exact-name Script selection and reconciles one installation per live matching root script, with an optional continuous single-instance precondition. `BML::Behavior::Plans` retains those intents across world epochs, observes script load and deletion before Mod callbacks or native teardown, and reconciles only at Loader safe points. Owner retirement first asks Plans to close their installations, then completes all owned Patch requests at the CK edit safe point, and finally collects Plans whose installations closed; this ordering keeps their callback state alive until native restoration finishes. Object deletion only drops the target: reconciliation waits for the next Loader frame instead of reaching into a graph Virtools is already deleting. Losing the last match leaves a single-instance Plan `Unsatisfied`; only an ambiguous match is a cardinality failure. A durable `PathRef` records an Entry or node Out and completes the unique logical Path again for each installation; `Tap` observes a node Out (Topology models Out taps only, so a graph Entry is rejected at Edit validation), while `After` observes the final node Out or serializes a HookBlock before a graph Exit. Each durable `Hook` owns one author callback occurrence and opens an independent `Binding` lease per installation, keeping Retain/Release state alive through native safe-point teardown. A spliced Hook Block sits inside a chain the host script owns, so when its callback does not run it stays transparent and passes the activation through; only a callback that completed and reported a CKBR error code stops the chain. CK2 discards a sub-behavior's return code, so the Hook Block stops the chain by leaving every Out inactive. A callback that faulted (threw, or returned the fault code the C++ facade substitutes for an exception) is a bug rather than a decision: the Binding keeps its first diagnostic, closes further admission for that occurrence, and the Block passes the activation through, matching how CK2 itself swallows a native BB's exception instead of stopping the graph. `BML::Behavior::Relations` is the private logical data-relation model: a normal Bind exclusively owns one existing Pin source, while the still-private Transform form is an explicitly ordered source layer. It rejects competing Binds before CK mutation and publishes multi-Pin changes atomically. `CKEdit` compares each published relation with its after-image during Close; a foreign source or Link endpoint, or a missing previous object, leaves the Patch `Conflicted` and retains a `RevertConflict`. Restoring the expected after-image allows the same Patch to retry its inverse. Each Pin records whether it has been handed back, so a retry touches only the Pins that are still out and never closes a Node the Runtime has already disowned; a Pin that disappeared with its port counts as settled. While any Pin is still out, the Patch keeps its relation claim and its key in the graph's active set, so no other owner can take the Pin and the same key cannot be applied over an unfinished teardown. Generic Node replacement is deliberately absent until it can transfer a node through the same native Lifecycle protocol; removing graph membership or moving Links and parameters is not teardown. A real `Physics Force` demonstrates the distinction: its Create activation returns `Ready` while its Local still names a controller registered with the IVP core. Runtime does not interpret that Local or maintain a table of stateful Prototypes. It uniformly retains every native Instance and uses CREATE/ATTACH/RESET/DETACH/DELETE at ownership boundaries; a BB's callbacks remain responsible for its own manager/world state. The production Player probe verifies dynamic In/Out/Pin/Pout, literal/direct/shared Bind, Push, `Tap/After`, exclusive relation admission, foreign-relation conflict with a partial multi-Pin revert and retry, durable reinstall across reset and graph recreation, exact Link restoration, balanced callback ownership, and the public one-graph Patch facade applying and restoring a real CK graph. Native Transform lowering and lifecycle-safe Node replacement remain later work.
_Avoid_: Behavior transport, Behavior service, execution facade, codec, object snapshotter, preflight capture

**Behavior Runtime**:
`BML::Behavior::Runtime`, the private Instance implementation behind Behavior Authoring and the loader's concrete Building Block modules. It resolves a Virtools Building Block Prototype, creates a configured instance, reflects its live layout, binds parameter values or sources, runs its callback lifecycle, and distinguishes immediate, persistent, graph-resident, and cross-frame execution. Settings are applied before final input binding because they may rebuild the instance layout. One loader runtime owns one Behavior Runtime.
The absence of a Prototype Execute function means callback-only, not graph-backed. Runtime initializes every Prototype instance with its native block data intact so CREATE can observe the declared Settings and callback state; only the provider may turn that live instance into a graph. A declared Layout therefore reports Function or Callback, while a live Layout reports Graph only when `CKBehavior::IsUsingFunction()` is false. Ballance's retail `CK2.dll` omits CREATE from `CallCallbackFunction`'s message-mask table, so Runtime dispatches CREATE from the current live block callback/mask/argument and uses native callback dispatch for every other lifecycle message.
Resolved slots carry the configured instance id and layout generation; a settings callback or execution makes old slot handles stale instead of silently retargeting an ordinal. Runtime records keep private CK ID-and-address stamps for owned objects; the public object-reference interface is not an internal lifetime mechanism. Literal and operation sources are Runtime-owned CK parameters rather than extra behaviors or parent locals. Their lifetime follows explicitly recorded managed input/source relations; multiple Runtime instances share those relations only when constructed to do so, and Runtime never infers ownership by scanning every parameter in `CKContext`. Raw relations created outside that shared ownership remain unmanaged. Normal release is delayed past native manager callbacks and sends DETACH/DELETE without misusing RESET; world reset explicitly closes retained state before discarding runtime records.
Detached execution is implemented by the private `BML::Behavior::Execution` module. It owns logical In admission, the one-Execute-per-frame rule, immutable active-Out Frames, bounded retention, and execution failures. `Runtime` is its CK2 adapter; deterministic tests use a fake adapter at the same seam. Ballanced makes `CKBehavior::IsActive()` after Execute the single native continuation fact: `ExecuteFunction` derives it from the retry bit, while `CheckBehaviorActivity` derives it from delayed Links and active or message-waiting children. The kernel consumes that native state without reproducing a function/graph scheduler or maintaining Prototype-specific rules. Building Blocks consume their own active In, while the execution implementation captures active Outs and every live Pout before clearing only those Outs. Unsupported Pout type, Pout read, or object-reference failure terminates the Run in that same native Frame; the Frame keeps the native sequence, active Outs, and capture diagnostic but no partial Pout batch. A `Ready` Run means the native Behavior is inactive and no accepted Pulse is queued; the Run still owns the native Instance, its Locals, and any provider-managed state until explicit Run/session/owner/world teardown.
Native configuration and teardown are implemented by the private `BML::Behavior::Lifecycle` module. It owns callback ordering, Setting replay, the placed/created/attached ledger, callback revalidation, compensating teardown, and deferred close admission; `Runtime` is its only CK2 adapter. Callback code is held through the private `BML::Behavior::Callback` lease protocol, which closes admission without waiting for the active invocation and retires callback state only at a game-thread safe point. Author Retain, Release, and invocation never run while the Session registry lock is held; a callback may therefore close its own Plan, Patch, Watch, Run, or Session without waiting or invalidating the registry iteration that admitted it. Script Hook Blocks use the same lease and lifecycle path rather than a separate active-call protocol.
_Avoid_: action cache, Building Block singleton, fixed pin table, synchronous-function wrapper, Virtools runtime

**Behavior Spec**:
`BML::Behavior::Spec`, the declarative interface between a named Building Block module and the Behavior Runtime. A spec contains only the Prototype GUID, slot selectors, values or sources, and setting stages; all creation, ownership, callback, execution, and destruction behavior remains in the Behavior Runtime. Each concrete Building Block keeps its options and spec construction in its own `src/Behavior/<BuildingBlock>.*` module rather than a shared spec collection.
_Avoid_: preset object, graph recipe, Building Block implementation, action module

**Physics Force**:
The `BML::Behavior::PhysicsForce` module, which owns the options, spec construction, and target-indexed sessions for persistent Virtools Physics Force instances. Create and Shutdown use the same configured instance because the Building Block stores its native controller in a Local. `PhysicsCallbackContainer::Process(callback)` first invokes Create synchronously; only a target without a PhysicsObject leaves the callback pending for a later simulation. Same-frame Set or Clear may queue Shutdown under Runtime's one-Execute-per-frame rule, so the session remains in its stopping state until Shutdown clears the old Local; an updating Set also retains the next requested force and creates a fresh instance only after that point. A deleting target leaves the active index immediately, while its instance remains in a retiring queue until a pending callback has observed cancellation or native Shutdown is complete. The Ballance Player probe waits for `OnBallNavActive`, then verifies that a `Ready` Create leaves a live controller, motion continues while the Instance is idle, Shutdown clears the Local, the last same-frame Set wins, and repeated Clear retires the session.
_Avoid_: force action cache, independent Set/Unset calls, force manager

**Object References**:
`BML::ObjectRefs`, the private module at the C and script interface seam that issues and resolves opaque `BML_ObjectRef` values. It observes normal CK object-deletion notifications and world reset, and rejects stale domain, generation, address, and deletion state. Behavior Runtime and Physics Force do not depend on this module; they keep their ownership and delayed-lifetime knowledge local. Objects deliberately destroyed with `CK_DESTROY_NONOTIFY` are outside this interface because CK managers cannot observe that lifecycle.
_Avoid_: CK identity registry, universal CK identity, Behavior object handle

**ExecuteBB Adapter**:
`BML::ExecuteBBAdapter`, the stateful adapter behind the exported `ExecuteBB` interface. It translates API calls into Behavior Specs and delegates them to the Behavior Runtime. The adapter belongs to the API seam; it is not part of the Behavior module and the Behavior module never depends on it.
_Avoid_: ExecuteBB runtime, Behavior implementation, Virtools adapter

## Source layout

The private source tree follows these runtime concepts instead of collecting unrelated code under generic `Core`, `Runtime`, or `Builtin` directories:

- `src/BML.cpp` is the loader composition root.
- `src/Mods/` contains concrete bundled `IMod` implementations. `BMLMod` assembles the built-in modules, while `NewBallTypeMod` is an independent bundled Mod.
- `src/Loader/` owns Mod discovery, registration, invocation, lifecycle, and CK manager integration.
- `src/Api/` adapts the public BML interfaces to loader-owned implementations, including Behavior Authoring, Object References, the `ExecuteBB` facade, and its stateful adapter.
- `src/Behavior/` contains owner-scoped Behavior Sessions, the Prototype Catalog, graph inspection/editing and durable Plans, shared Layout and Parameter semantics, and the Behavior Runtime. Named Building Block definitions are header-only adapters under `include/BML/Behavior/Blocks/`; the private `Blocks::Detail::Definition` lowers the same definition into a Runtime Spec. Only stateful services such as Physics Force sessions and the live Text2D view remain private modules. These modules depend on CK infrastructure but never on `Loader` or `Api`; the Runtime never depends on a concrete Building Block.
- `src/Console/`, `src/HUD/`, and `src/CustomMaps/` contain the Built-in Console, Built-in HUD, and Built-in Custom Maps modules respectively.
- `src/Gameplay/` contains the loader-owned game session, game event hooks, and gameplay tweaks.
- `src/Config/`, `src/DataShare/`, `src/Imc/`, and `src/Logging/` each keep one cross-cutting runtime concern local.
- `src/UI/` contains concrete UI such as the Mod menu; `src/Hooks/` contains process and engine hooks; `src/Virtools/` contains only shared low-level CK graph helpers that do not belong to a deeper runtime module. The Hook Block Prototype, registration, execution, and spec all belong to `src/Behavior/HookBlock.*`.
- `src/AngelScript/` and `src/Utils/` remain independently navigable implementation families.

Private includes use these directory names explicitly, so a caller reveals which module interface it crosses.

## Example dialogue

> **Developer:** Should command history be saved by the Built-in Loader Mod?
>
> **Domain expert:** No. Command history belongs to the Built-in Console; the Built-in Loader Mod only tells it when loading and unloading occur.
>
> **Developer:** Should the Built-in Loader Mod update the speedrun timer and HUD elements itself?
>
> **Domain expert:** No. Those belong to the Built-in HUD; the Built-in Loader Mod only forwards game lifecycle events.

> **Developer:** Should the Built-in Loader Mod know which Virtools parameters a custom map load changes?
>
> **Domain expert:** No. Those bindings and the loading sequence belong to Built-in Custom Maps; the Built-in Loader Mod only forwards the relevant object, script, and game lifecycle events.

> **Developer:** Does the Overclock graph state belong to Built-in Game Event Hooks because both inspect gameplay scripts?
>
> **Domain expert:** No. Built-in Game Event Hooks only translate game transitions into callbacks. Overclock and the other configurable corrections belong to Built-in Gameplay Tweaks.
